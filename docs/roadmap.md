# DeskPal 路线图

2026-11-13 重写。之后按「房间互动 → 游戏核心 → 游戏里的房间互动 → 上架 Steam」的顺序推进。每一项开始前，先在 [progress.md](progress.md) 的「已定」里写清楚口径。标了「待决定」的地方要先确认再动手。

## 一、两条不能破坏的原则

所有新功能先过这两条，过不了就不做。

### 1. 不提供任何语言沟通的能力

- 不做：聊天、私信、留言、评论、自定义状态文字、房间公告、礼物附言、可以自由组合的表情或贴纸。
- 允许：固定的、不带自定义内容的动作，例如赠送一件道具、在小屋里摆放一个摆件。动作种类要少，避免组合起来变成暗号。
- 显示名称和房间名是现有的例外，保持长度限制。新功能不再增加别人能看到的自由文本，宠物和摆件不能命名。

### 2. 不被其他成员的主动操作引发的通知打扰

- 判定方法：凡是别人点了某个按钮才发生的事（赠送、摆放、发起专注时段），结果只出现在「自己去看」的地方，也就是打开面板后的房间页、背包、统计页。
- 不做：托盘气泡、Windows 通知、声音、托盘图标闪烁或角标、任务栏闪烁、自动弹出面板、未读数字，也不在置顶小卡片和桌宠上即时播放动画。
- 别人的状态变化（开始工作、上线、离开）不是主动操作，照常显示在状态页和置顶小卡片上，这是产品本身。但同样不弹通知、不发声音。
- 由别人状态触发的提醒也不做，哪怕是自己订阅的，例如「对方空闲时提醒」。

由这两条得出新互动的三个特征：**没有语言、不会来找你、你去看时才看到**。另外延续阶段 3 的防滥用口径：房间内权限对等，不做单向查看，不按工作时长排名。

## 二、现状

已经完成：多房间（同一时间进入一个，可选无房间）、状态共享和按类别的隐私设置、个人分类和规则库自动改进、使用统计和按房间公开、屏蔽成员、置顶小卡片、单点登录、简体中文和英文、自动更新和安装向导。

## 三、不再计划和调整

| 项目 | 处理 | 原因 |
|---|---|---|
| Refresh token | 不做 | 上架 Steam 后，每次启动用 Steam 会话票据换取 token；在那之前 30 天重新登录一次可以接受 |
| 浏览器扩展 | 不做 | 要单独上架和维护，Steam 用户不会为此装扩展。接受 UI Automation 的已知问题（见 [known-issues.md](known-issues.md)） |
| 手机端查看 | 不做 | 和桌宠、游戏方向无关 |
| 摸鱼同步提醒 | 删除 | 「聊两句」引导语言沟通，弹出提醒又是打扰，违反两条原则。改为阶段 A 的「同步标记」，只做被动显示 |
| 对方空闲时提醒 | 删除 | 提醒本身就是打扰 |
| 代码签名 | 暂缓 | Steam 分发不经过浏览器下载，不会出现 SmartScreen 提示。只有决定长期保留独立安装包时再考虑 |
| 公开统计在本人离线时也能看 | 暂缓 | 要把加密汇总放到 Server，收益不大 |

下面这些是试用期的临时设施，**保持可用、只修影响试用的问题、不再扩展**：账号密码登录、注册邀请码、Inno Setup 安装向导、Velopack 自动更新和测试版通道、GitHub Release 分发。上架 Steam 后是否保留独立版见第九节。

## 四、阶段 A：房间互动（不依赖游戏，先做）

目的：验证「没有语言、不打扰」的互动有没有人用，同时攒下游戏要用的数据（一起在线的时长、连续天数）。

注意数据来源：Server 不解析状态的 Payload（硬约束 3），所以房间层面的数字不能由 Server 从状态里计算。下面每一项都写明数据从哪里来。

| 功能 | 做法 | 数据来源 |
|---|---|---|
| 一起工作 | 状态页顶部一行：「房间里 3 人在工作中，今天一起工作了 2 小时 10 分」。只统计自己能看到的成员，屏蔽的不算 | 每个客户端按收到的状态自己推算，不需要新消息 |
| 同步标记 | 两人以上同时在看视频或在玩游戏时，成员行上出现一个小标记；隐私设置允许看到应用名、并且是同一个应用时换成另一种标记。不提示，不出现「去聊聊」之类的引导 | 客户端按收到的状态判断 |
| 专注时段 | 任何成员都可以在房间页开始 25 或 50 分钟的专注时段。其他人打开面板时看到「正在专注，还剩 18 分钟」，可以自己点「加入」。不邀请、不通知。结束时只在参与者自己的面板上记一笔；自己发起或加入的时段结束时，可以选择提醒自己 | 结束时间放进自己的状态里（新字段），Server 照常转发和补发，不需要新消息类型 |
| 成就和连续天数 | 连续 7 天上线、累计工作 100 小时这类成就，从本机使用统计计算。按房间选择是否在成员行上显示徽章。自己解锁时只在自己的面板上显示 | 本机计算；显示的徽章放进状态。以后对应 Steam 成就 |
| 房间周历（待决定） | 房间页显示本周每人每天是否上线的格子，只有在线时长，不分类别 | 需要 Server 保存每人每天的在线分钟数，要改硬约束 4。不改的话只能显示自己在线时看到的部分，数据不全 |

建议先做「一起工作」和「专注时段」：前者不用改协议，后者是第一个「别人发起、你自己决定要不要参与」的互动，可以检验第二条原则的实际体验。

## 五、阶段 B：游戏核心（桌宠和挂机收集）

| 功能 | 要点 |
|---|---|
| 桌宠窗口 | WPF 原生透明窗口（[ui-tech-evaluation.md](ui-tech-evaluation.md) 已验证，同样的动画 CPU 约 9%，静止时接近 0）。动作跟随自己的状态和输入：打字时敲键盘，空闲时睡觉，锁屏时离开。可以关掉 |
| 输入计数 | Raw Input 只计键盘和鼠标点击的次数，不读按键内容，作为新的 `ActivitySignal`，不进入状态判断（skill `deskpal-add-signal`）。要先在装了 EDR 的公司电脑上验证后台接收输入（`RIDEV_INPUTSINK`）不会被拦截 |
| 掉落（待决定依据） | 建议以在线时长为主：每在线一段时间掉一件，每天有上限；输入次数只驱动动画和少量加成。这样不评判在工作还是在放松（界面已经不用「摸鱼」），连点器也没有意义 |
| 道具 | 只有外观：宠物皮肤、帽子、配饰、小屋摆件。不影响任何数值 |
| Server `Features/Game` | 掉落由 Server 按连接时长判定，不接受客户端提交的掉落结果；道具归属写入数据库（硬约束 4 要加一项）。新增 `game.*` 消息类型（skill `deskpal-add-message-type`）。游戏消息是 Server 自己要读的，和状态消息分开，不放进以后的端到端加密 |
| 单人也成立 | Steam 上的新用户第一次打开时，大多没有朋友在房间里。无房间时也要有桌宠、掉落和背包，房间是加分项而不是前提 |

## 六、阶段 C：游戏里的房间互动

核心想法是「**在一起就更快**」：不用说话，只要同时在线就有好处。

| 功能 | 做法 | 两条原则怎么保证 |
|---|---|---|
| 同房间加成 | 当前房间里同时在线的人越多，掉落越快（例如每多一人加 10%，有上限）。Server 本来就知道谁在线，不需要解析 Payload | 没有任何主动操作 |
| 房间小屋 | 房间页有一个共享场景，每个成员的宠物在里面按状态活动；成员可以把自己的摆件放进小屋 | 摆放是主动操作，别人下次打开房间页时才看到，没有提示 |
| 赠送道具 | 把一件道具送给房间成员，不能附言。对方下次打开背包时看到「来自某某」 | 没有未读数，托盘和桌宠都不变化 |
| 房间共同目标 | 每周一个目标（例如房间一起在线 40 小时），完成后全员得到同一件纪念外观 | 进度只在房间页显示 |
| 同步彩蛋 | 同时在玩游戏时宠物戴上同款耳机，同时在工作中时小屋亮灯 | 由状态自动触发 |
| 置顶小卡片换成宠物 | 置顶的成员显示为他的宠物，动作跟随他的状态 | 只跟随状态；赠送、摆放不在卡片上播放 |

明确不做的互动：

| 想法 | 违反 |
|---|---|
| 表情回应、点赞、戳一下 | 第二条（对方会被提醒）；表情多了也会变成语言 |
| 宠物跑到别人的桌面上串门 | 第二条，直接出现在对方屏幕上 |
| 上线提醒、催促、叫醒 | 第二条 |
| 礼物附言、房间公告、宠物命名 | 第一条 |
| 按工作时长的排行榜 | 防滥用，容易变成考勤 |

## 七、阶段 D：上架 Steam

建议在阶段 B 进行时就先做一次 Steamworks 技术验证，因为登录方式和道具存在哪里会影响阶段 B 的数据结构。

| 事项 | 要点 |
|---|---|
| 接入 | Steamworks.NET；启动时调用 `SteamAPI_RestartAppIfNecessary`。需要 Steamworks 开发者账号，每个应用要交上架费（目前 100 美元），并填写税务和银行信息 |
| 登录 | 客户端用 `GetAuthTicketForWebApi` 取会话票据，Server 调用 Steam Web API `ISteamUserAuth/AuthenticateUserTicket` 验证后签发 JWT，账号按 SteamID 建立。去掉密码和注册邀请码；单点登录的口径要重新确认。现有试用账号是否迁移待决定 |
| 安装和更新 | Steam 版由 Steam 负责，不再使用 Inno Setup 和 Velopack。`CHANGELOG.md` 和更新内容弹窗可以保留 |
| 房间邀请 | 保留邀请码。Steam 好友邀请依赖 Steam Overlay，要验证在 WPF 和 WebView2 窗口里能不能用，不能用就只保留邀请码 |
| 道具存储（待决定） | 建议先放在自己的 Server，不能交易。Steam Inventory 可以交易，但最近几年出现过大量「挂机掉落可交易物品」的应用，Valve 在收紧这类应用的审核和交易限制，上架前要查当时的 Steamworks 规则 |
| 成就和统计 | 阶段 A 的成就对应 Steam 成就 |
| Rich Presence | 可以在 Steam 好友列表显示「工作中」。默认关闭，单独开关，因为 Steam 好友不等于房间成员 |
| Steam Cloud | 可以解决换电脑要手动导入导出统计的问题。但统计里有窗口标题，按硬约束 2 只能同步去掉标题的部分，或者加密后再同步 |
| 自身分类 | Steam 版装在 `steamapps` 下，推测层会把 DeskPal 自己的面板归为在玩游戏，要排除自身进程 |
| 开机自启 | Steam 版要经过 Steam 启动，开机时 Steam 可能还没就绪，要实测 |
| Server 部署 | 现在是家用服务器加 36443 端口。对外发布要换到云服务器和 443 端口；面向国内用户还涉及 ICP 备案，海外用户多了要考虑海外节点 |
| 合规 | 隐私政策；国内《个人信息保护法》（单独同意、数据最小化）和海外 GDPR（导出、删除账号数据） |

## 八、以后（可选）

- 创意工坊：用户上传宠物皮肤和摆件。
- 端到端加密：成员本地生成密钥对，Room 密钥在成员之间分发，成员退出时轮换；`Envelope.Enc` 改为加密算法标识，Payload 改为密文，Server 不需要改。`game.*` 消息不加密。
- 数据库按需从 SQLite 换成 PostgreSQL（换 EF Core Provider，重新生成迁移）。
- 季节活动和限定外观。

## 九、待决定和头脑风暴

### 需要先定的问题

| 问题 | 选项和建议 |
|---|---|
| 产品定位 | 「带游戏的状态共享工具」还是「带状态共享的挂机游戏」。影响店铺分类、首次打开的体验和宣传重点。建议后者：Steam 用户是冲着桌宠和收集来的，状态共享让它和别的挂机游戏不一样 |
| 掉落依据 | 按在线时长、按输入次数，还是按工作时长。建议按在线时长，理由见阶段 B |
| 道具能不能赠送、交易 | 只能赠送给房间成员、完全不能流通，或接入 Steam 交易。建议先只能赠送 |
| 收费方式 | 免费加外观 DLC（支持者包）、低价买断，或完全免费。Bongo Cat 是免费加道具 |
| 是否保留独立版 | 很多公司电脑不允许装 Steam，上班开着 Steam 也不合适，而 DeskPal 的主要使用场景就是上班。可以同时保留独立版（现在这套安装和更新），账号互通 |
| 房间历史能不能存在 Server | 只存每人每天的在线分钟数，房间周历和房间共同目标才能做准确。要改硬约束 4 |

### 可以继续想的方向

- **公开自习室**：Steam 上有很多人想「有人陪着学习或工作」。因为没有语言沟通，陌生人一起进一个公开房间也几乎没有骚扰的可能，只看彼此的状态和宠物。默认所有类别只显示状态，不能查看统计。这可能是对外宣传最容易讲清楚的卖点。
- **陪伴感而不是监督感**：所有房间数字都写成「一起工作了多久」，不写「谁工作得最多」。对比只和自己的昨天、上周比。
- **桌宠就是头像**：房间成员、置顶小卡片、小屋里都用同一只宠物表示一个人。外观是收集的目标，也是在房间里的存在感。
- **按状态换装**：宠物在工作中时戴眼镜、在玩游戏时拿手柄、暂离时趴着。自己的状态变化让宠物有变化，不需要任何主动操作。
- **一天的回放**：晚上打开统计页时，用宠物的动作把自己这一天的状态时间轴播放一遍，只给自己看。

## 十、技术风险

- Raw Input 后台接收输入在部分 EDR 上的表现没有验证，验证不通过时输入计数只能在自己的窗口获得焦点时统计，或者放弃，掉落只按在线时长。
- 桌宠窗口常驻的内存和 CPU 要在低配电脑上实测；现在面板隐藏 5 分钟后释放 WebView2，桌宠不能把这部分省下来的资源再占回去。
- Steam 版和独立版并存时，登录、更新、道具存储都有两套，测试量翻倍。
- 掉落按连接时长计算后，挂着不用也能拿到。用已有的空闲和锁屏判定暂停计时，再加每天上限，不另外检测人在不在电脑前。
