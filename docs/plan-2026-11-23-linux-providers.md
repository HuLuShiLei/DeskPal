# Linux 版与识别插件（provider）

状态：**已实现（2026-11-23），随后按用户要求扩展为三个平台的插件系统**，见 [changes-2026-11-23-plugins.md](changes-2026-11-23-plugins.md)；下文“只给 Linux 开放”“同一时间只用一个识别来源”“内置来源不读浏览器网址”等已被第二轮取代。第一轮，实际改动和验证结果见 [changes-2026-11-23-linux.md](changes-2026-11-23-linux.md)。下面是动手之前的方案记录，保留作为取舍的依据；标「建议」的做法里，用户没有逐条确认的都按建议执行了，「待定」一节末尾写了每一项最后怎么定的。

## 做什么

1. 做 Linux 客户端，和 Windows、macOS 用户在同一个房间，Server 不改。
2. Linux 上「当前在用哪个应用」没有统一的取法，每种桌面环境都不一样。所以把这部分做成接口，由识别插件（provider）提供；DeskPal 自带一个默认插件，覆盖常见和基础的情况，其余环境允许用户自己写插件。
3. 提供写插件的教程：一份文档给人看，一个 skill 给 AI 用。

## 已定

- **插件只在 Linux 上开放。** Windows 和 macOS 继续用内置的采集器，行为不变，暂时不提供插件入口。以后要不要开放再说，届时沿用同一套协议。
- **自带默认插件**，覆盖大部分和基础的情况；其余由用户按自己的系统环境和软件写插件。
- **要有插件教程**：给人看的文档，加一个给 AI 用的 skill。实现插件机制时一起交付，不能漏。
- 朋友的环境是 Ubuntu 和 Arch 各一台，先以这两台为目标。
- Linux 客户端和 macOS 版一样用 .NET，复用 `DeskPal.Client.App`、`DeskPal.Client.Core`、`DeskPal.Shared` 和 `src/DeskPal.Client/web`。

## 可行性（摘要）

| 信号或功能 | X11 | Wayland |
|---|---|---|
| 前台应用、窗口标题、全屏 | 读窗口属性，不需要权限 | 没有统一接口：GNOME 要扩展，KDE 用 KWin 脚本，Sway、Hyprland 用各自的接口 |
| 浏览器网址 | 通过辅助功能（AT-SPI）读地址栏，要实测 | 同左 |
| 空闲 | X11 屏保扩展 | `ext-idle-notify` 协议；GNOME 用 `org.gnome.Mutter.IdleMonitor` |
| 锁屏 | systemd-logind 或屏保的 D-Bus 信号 | 同左 |
| 媒体播放 | MPRIS | 同左 |
| 托盘图标 | 可以 | GNOME 要 AppIndicator 扩展（Ubuntu 默认带） |
| 面板定位、置顶小卡片 | 可以 | 程序不能自己定位和置顶；GNOME 上也许能由自带扩展代做，要实测 |
| 开机自启、通知、本机密钥、单实例 | autostart 目录、通知 D-Bus 接口；密钥文件和单实例锁沿用 macOS 版写法 | 同左 |
| 安装和更新 | Velopack 的 AppImage | 同左 |

其他限制：

- 不能用 Flatpak 或 Snap 发布，沙盒会挡住读取其他窗口和进程。
- 界面依赖系统里的 WebKitGTK 6.0 和 GTK4，最低支持的发行版版本要实测后定。
- 标题栏拖动不能用 macOS 版「窗口跟随鼠标」的做法，要用 GTK 的拖动接口。
- 空闲检测不读 `/dev/input`：那需要额外权限，效果上等于能读按键，违反硬约束。

## 插件机制

### 接口位置

现在的采集器各自往 `ActivityBus` 发信号（`ForegroundSignal`、`BrowserDomainSignal`、`IdleSignal`、`LockSignal`、`MediaSignal`），分类、防抖、不记录标题、隐私过滤都在后面。插件就是「谁来发这些信号」，后面的流程不变，插件输出的内容照常经过隐私过滤。

### 建议：插件是外部程序，不是 .NET DLL

DeskPal 启动一个可执行文件或脚本，它往标准输出每行写一条 JSON，例如：

```json
{"v":1,"type":"foreground","process":"firefox","name":"Firefox","title":"…","fullscreen":false}
```

理由：

- 门槛低：用 bash 或 Python 几行就能写，不需要 .NET SDK。例如 Hyprland 上包一下 `hyprctl activewindow -j`。
- 隔离：插件崩溃或卡住时重启它即可。DLL 在进程内，能读到登录 token 和统计库。
- 没有二进制兼容问题：协议带版本号 `v`，不跟着 .NET 版本和内部类型走。

GNOME 的情况：默认插件里有一段去调自带扩展的 D-Bus 接口，再转成同样的 JSON。

### 建议：范围

- 只有前台窗口和浏览器网址可以由插件提供。空闲、锁屏、媒体在 Linux 上有标准接口，内置。
- 协议和加载逻辑放在共享层（`DeskPal.Client.App`），只在 Linux 上启用。
- 选择顺序：用户指定的插件优先；没有指定时用默认插件，它按环境自动判断（X11、GNOME 扩展、KDE、Sway/Hyprland）。
- 默认插件先覆盖朋友的两台电脑，再视情况补其他环境。

### 要守住的

- 硬约束（不截图、不读按键内容）管不到第三方插件。所以：插件只能输出协议里固定的字段；只从用户配置目录加载，要用户手动启用；设置页显示当前用的是哪个插件。
- 协议公开后就是对外承诺，改字段要保持兼容。
- 日志里记录每条信号来自哪个插件，方便区分是谁的问题。

### 针对单个软件的增强插件

「给某个软件写插件」和「给系统环境写插件」不同：前者是在前台是这个软件时补充详情（终端里在跑什么、编辑器开的哪个项目），涉及详情里能放什么，和隐私级别有关。建议第一版不做，协议里留出位置。

## 待定

1. **插件形式**：外部程序加 JSON（建议），还是 .NET DLL。
2. **GNOME 扩展**：是否接受让用户启用一个 DeskPal 自带的扩展（启用后要注销重新登录一次）。不接受的话，GNOME + Wayland 上只能共享在线、暂离、锁屏和正在播放的媒体。
3. **针对单个软件的增强插件**：第一版做不做（建议不做）。
4. **Arch 那台的环境**：同一组命令的输出。
5. **GNOME Shell 版本**：Ubuntu 26.04 上显示 46.0，要 `apt policy gnome-shell | head -3` 和 `gnome-extensions list --enabled` 的输出来确认，扩展要声明支持哪些版本。
6. **发布形式**：只出 AppImage（建议），还是另外维护 AUR 包。
7. **Wayland 上做不到的功能**：置顶小卡片和面板定位是去掉，还是降级成普通窗口。
8. **读不到浏览器网址时**：只显示「在浏览网页」加标题是否可以接受。
9. **朋友用的浏览器和安装方式**（Ubuntu 的 Firefox 默认是 Snap 版）。
10. **测试**：Ubuntu 可以用虚拟机，Arch 加上他自己的桌面配置要他本人帮忙测。
